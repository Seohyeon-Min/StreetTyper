# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**스트리트타이퍼 (Street Typer)** is a Unity project (Editor version **6000.3.19f1**, Universal Render Pipeline, 2D template) — a turn-based "typing action text RPG" prototype (10-day prototype scope per the design doc). Core loop: on the player's turn, 5 word "cards" are always shown on screen; the player types them back-to-back with **no spaces or Enter needed** to build a combo before a countdown timer runs out. Words fall into 3 categories (this maps directly onto the `CardData` type hierarchy — see Architecture below):

- **수식어 (Modifier)** — stat-amplifying words (e.g. 슈퍼 +1, 울트라 +2, 파워 amplifies the next modifier, 어썸 scales with success count, 퀵 adds timer time).
- **속성/특수효과 (Attribute)** — status effects and combat modifiers (burn/paralysis/freeze chance, life drain, damage reduction, crit, repeat-action).
- **액션 (Action)** — attack/defense words that resolve a combo (펀치/잽/훅/어퍼컷/페인트/뎀프시롤/가드), each with its own power bonus, timer delta, and special rules (ignores/breaks defense, combo re-trigger chance).

**Current implementation scope**: the typing/input pipeline and the card-matching/combo-buffer system are built. Actual combat resolution (damage math, timer countdown, status effects, enemy AI, HP) described in the design doc is **not implemented yet** — that data exists on the `CardData` subclasses (see below) but nothing consumes it yet. Don't assume combat systems exist; check before building on top of them.

## Working with this repository

This is a Unity project, not an npm/CLI project — there are no build/lint/test scripts to invoke from the terminal. Standard Unity workflow applies:

- **Editor**: Open the project root in Unity Hub / Unity Editor `6000.3.19f1` (must match `ProjectSettings/ProjectVersion.txt`).
- **Compiling scripts**: Unity compiles C# automatically on focus/save. No standalone `dotnet build` step — `Assembly-CSharp.csproj`/`StreetTyper.sln` are auto-generated by Unity and gitignored; never hand-edit them. Single implicit `Assembly-CSharp` assembly, no `.asmdef` split.
- **Tests**: `com.unity.test-framework` is installed but unused — no test assemblies exist. "Testing" in this repo currently means manual Play Mode verification (see the Deck Manager section below for the pattern used so far).
- **Running the game**: Press Play in the Editor. No headless/CLI run path exists.
- C# `LangVersion` 9.0, .NET Standard 2.1 (Unity Mono backend) — avoid newer C# syntax the compiler won't accept.

## Project structure

Assets are organized under numbered top-level folders (controls asset browser ordering) — follow this `NN_Name` convention for new top-level folders:

- `Assets/00_Scenes/SampleScene.unity` — the only scene. Root hierarchy convention: `00_BOOT`, `01_CAMERA`, `02_SYSTEM` (manager objects like `InputManager`, `Deck Manager` live here), `03_WORLD`, `04_UI` (Canvas, card slot views, the input display field), `05_DEBUG`, plus `EventSystem` and a `DontDestroyOnLoad` root.
- `Assets/01_Arts/Fonts/` — includes `Paperlogy-4Regular SDF.asset`, a TMP font asset that **includes Hangul glyphs**. Any new `TMP_Text`/`TMP_InputField` displaying Korean must use this font asset — the default `LiberationSans SDF` is Latin-only and will silently render missing Korean glyphs as `□` with a console warning per character.
- `Assets/02_Scripts/InputManager/` and `Assets/02_Scripts/Deck Manager/` — see Architecture below.
- `Assets/04_Data/Cards/` — `CardData` ScriptableObject instances (test data), created via the Editor's `Assets > Create > Deck Manager > Cards > ...` menu, not hand-authored `.asset` YAML (asset creation should always go through `[CreateAssetMenu]` + the Editor GUI in this project — hand-written `.asset` files risk silently mismatched GUIDs).
- `Assets/TextMesh Pro/` — imported TMP Essentials resources.
- `Assets/InputSystem_Actions.inputactions` — the new Input System's default action-map asset. **Not used** by the typing/gameplay input — see below.

## Architecture

### Input pipeline (`Assets/02_Scripts/InputManager/`)

Gameplay typing input deliberately bypasses Unity's Input Action asset/bindings system entirely (`InputSystem_Actions.inputactions` is still the untouched default template — don't wire gameplay to it). Instead:

- **`InputManager`** polls `UnityEngine.InputSystem.Keyboard.current` directly. It exposes `CurrentInput` (accumulated committed alphabet/Hangul characters since the last clear), `Composition` (in-progress, not-yet-committed IME composition text), and events `OnCharacterEntered(char)`, `OnBackspace`, `OnSubmit` (Enter/Numpad Enter only), `OnCompositionChanged`, `OnInputCleared`. Public control via `EnableInput()`/`DisableInput()`/`ClearInput()`; auto-enables itself in `Start()`.
  - Character capture uses `Keyboard.onTextInput` (filtered to `IsAlphabet`/`IsHangul` ranges), not raw key polling — this is what gives correct-cased/composed characters including Hangul.
  - Korean IME composition is handled via `onIMECompositionChange` + `SetIMEEnabled(true)`. Backspace is deliberately suppressed while a composition is in progress (`Composition` non-empty) so it edits the IME's own composition buffer instead of double-deleting already-committed `CurrentInput` characters.
  - Backspace has hold-to-repeat (`backspaceRepeatDelay`/`backspaceRepeatInterval`).
- **`InputFieldDisplay`** is a pure view: mirrors `CurrentInput + Composition` into a **read-only** `TMP_InputField` (`readOnly = true` — it must never accept its own keyboard/IME focus, since `InputManager` already owns the OS-level IME context; making it interactive causes double-input handling). It also calls `Keyboard.current.SetIMECursorPosition(...)` (computed from the TMP text's last-character screen position) so the OS's native IME composition overlay draws in the right place.

**Known unresolved issue**: in Editor Play Mode, the 한/영 (Hangul/English) IME toggle key sometimes stops working *only* while the Unity window has focus (works fine elsewhere on the same machine, including Unity's own Inspector fields). A native workaround was attempted (`GetAsyncKeyState` polling `VK_HANGUL` + `ImmSimulateHotKey` via P/Invoke in `InputManager`) but had no effect and was reverted. Root cause is still unresolved — don't blindly re-attempt that exact fix; something in Unity's Input System raw-input handling on this specific machine/setup needs deeper investigation first.

### Deck Manager / card system (`Assets/02_Scripts/Deck Manager/`)

Implements the "5 word slots + typing combo" mechanic from the design doc, independent of `InputSystem_Actions`:

- **`Cards/CardBase.cs`** — abstract `ScriptableObject` (`CardName` — the exact word to type/display and the matching key, `Icon`, `Description`, abstract `Category`) plus `enum CardCategory { Modifier, Attribute, Action }`. Three concrete subclasses (`ModifierCardData`, `AttributeCardData`, `ActionCardData`) map 1:1 to the design doc's three word tables, each modeling its whole category with an effect-type enum + a few numeric fields rather than one C# subclass per word. **These carry data only — no damage/timer/status-effect execution logic exists yet**, by design (deferred until a combat system exists).
- **`CardSlotManager`** — owns the 5 on-screen slots (`CurrentCards`, `OnSlotChanged` event), fills them from a serialized `availableCards` pool uniformly at random (**duplicates across slots are allowed by design** — a no-duplicate variant was built and then reverted per explicit request, so don't "fix" this without checking first).
- **`CardInputHandler`** — the matching logic. Subscribes only to `InputManager.OnCharacterEntered` (real-time, per keystroke — `OnSubmit`/Enter is intentionally not used for matching). Each keystroke: exact match against one of the 5 current cards → consume (buffer + refill + clear input); still a valid prefix of at least one card → wait; not a prefix of any → typo → clear the buffer + clear input.
  - **Known gap — Hangul cards can fail to match**: `OnCharacterEntered`/`CurrentInput` only reflect IME-*committed* characters (see Input pipeline above); mid-composition jamo live in `Composition` and are invisible to `CardInputHandler`. For a multi-syllable Hangul `CardName`, every syllable before the last commits normally as soon as the next syllable's composition starts, but the **last syllable of the word has no subsequent keystroke to force its commit**, so it can sit in `Composition` forever and never reach `HandleCharacterEntered` — the card silently never matches no matter how correctly it's typed. English cards are unaffected (no IME composition step). Not yet fixed; a fix would need `CardInputHandler` to also consider `InputManager.Composition` (e.g. match against `CurrentInput + Composition`), which touches the core matching logic — confirm the approach before changing it.
- **`MainBufferManager`** — ordered list of successfully-typed cards this run (`AddCard`/`ClearBuffer`, `OnCardAdded`/`OnBufferCleared`). Every matched card is appended uniformly regardless of category — it does not auto-flush/execute on Action-card matches (that's future combat-system work).
- **`UI/CardSlotView`** — displays one slot's `CardName`/`Icon`, self-subscribing to `CardSlotManager.OnSlotChanged` by a per-instance `slotIndex` (0–4, set in the Inspector — a common setup mistake is forgetting to change this on duplicated slot objects, since they'll all silently mirror slot 0). Tolerates a null `Icon`.
- **`DeckManager`** — thin read-only facade over the other three managers + `InputManager` (no central wiring logic needed, since every component wires itself via direct `[SerializeField]` references). Has an optional `logDebugEvents` flag that `Debug.Log`s match/typo/buffer events — currently the only way to manually verify buffer state, since no combat/HUD UI exists yet to visualize it.

All four Deck Manager components are meant to sit as sibling components on one "Deck Manager" GameObject; `CardSlotView` instances live separately under the UI canvas.

## Conventions

- No C# namespaces anywhere — all classes are in the global namespace.
- No singletons/service locators/DI framework: every cross-component dependency is a plain `[SerializeField]` reference wired by hand in the Inspector.
- Logic vs. view separation: "manager" scripts (`InputManager`, `CardSlotManager`, `CardInputHandler`, `MainBufferManager`) own state/decisions; "view" scripts (`InputFieldDisplay`, `CardSlotView`) only mirror that state onto UI and never make gameplay decisions themselves.
- Event-driven wiring throughout (plain C# `event Action`/`event Action<T>`), subscribed in `OnEnable` and unsubscribed in `OnDisable`.
- Folder/file naming occasionally reflects intentional user choices (e.g. the `Deck Manager` folder has a space in its name) — this is not a typo to "fix". Actual past typos (`InputManger` → `InputManager`, `DeckManger.cs` → `DeckManager.cs`) have already been corrected once; don't reintroduce naming drift or rename things further without being asked.
